One missing check, other people's private AI sessions

A developer platform's AI-agent feature exposed one user's private sessions to another. The query that served them never checked who owned the record. I found it by reading the authorization code, then proved it against live production with two separate accounts — and an independent reporter and the vendor's own team confirmed it was real.

What it was

The feature lets a team run AI agent workflows, and each workflow session is meant to be private to the user who created it. A GraphQL query returned those sessions, and the policy object behind it validated that the caller was a member of the right context — but never that the caller actually owned, or had been granted access to, the specific records it returned. The ownership predicate simply was not there.

The practical effect: a low-privilege member of a workspace — the Developer role, not an admin — could read other users' private agent sessions through a normal API call. For a platform where those sessions can carry source code, prompts and internal context, that is a straightforward confidentiality breach across a trust boundary that is supposed to hold.

How I found it, and how I proved it

This started in the source. I read the policy and the resolver for the query and saw the gap directly: the authorization layer checked membership but not record ownership, so the row filter an attacker needed to clear was never applied to them. That is the kind of bug you cannot find by fuzzing — you have to read the code and understand what the check is and is not doing.

Finding it in the source is only half the job; the part that counts is proving it. My first write-up was closed because the proof was not strong enough — I had reproduced it on a self-managed instance rather than the live target. So I rebuilt the whole thing: two independently controlled accounts on live production, each verified as a real user of the feature, no modification to the platform's source of any kind, and two screen recordings covering the full chain end to end. One account's private sessions, read in full from the other. That is the version that stands.

How it resolved

It was closed as a duplicate: another researcher had reported the same missing check. No bounty — duplicates pay nothing — but that outcome is the clearest external confirmation a finding can get. An independent reporter saw the same bug, and the vendor's triage team agreed it was one. The analysis was right and the proof held; someone else simply got there first.

The target stays unnamed here: the report was handled privately and was never publicly disclosed.

What it shows

Reading real authorization code to find a gap a scanner never would, then backing it with a clean, reproducible proof on the live system — and rebuilding that proof to a higher standard when the first one fell short. That is the work.
