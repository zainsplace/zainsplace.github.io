One missing check, other people's private AI sessions

A developer platform's AI-agent feature let one user read another user's private sessions. The query that returned them never checked who owned the record. I found it by reading the authorisation code, then proved it on live production with two separate accounts.

What it was

The feature lets a team run AI agent workflows, and each session is meant to be private to whoever created it. A GraphQL query returned those sessions. The policy behind it checked that the caller belonged to the right workspace, but not that they owned, or had been given access to, the specific records coming back. The ownership check just wasn't there.

So a low-privilege member of a workspace, on the Developer role rather than admin, could read other people's private agent sessions through a normal API call. Those sessions can hold source code, prompts and internal context, so this crossed a boundary that is meant to hold.

How I found it

This one started in the source. Reading the policy and the resolver for the query, the gap was right there: the check looked at membership but not ownership, so the row filter an attacker should have had to clear never applied to them. You do not catch that by fuzzing. You read the code and work out what the check does and does not do.

Finding it is the easy half. My first attempt was closed for weak evidence, because I had reproduced it on a self-managed instance instead of the live target. So I did it again properly: two separate accounts on live production, each a real user of the feature, no changes to the platform's source, and screen recordings of the whole chain. One account's private sessions, read in full from the other.
