An SSRF the docs said couldn't happen

A managed cloud database let me point its snapshot-restore feature at any URL I liked, with nothing but a normal API key, and the backend would go and fetch it. The product's own docs said this was blocked in the cloud. The source said otherwise, and so did twenty-two out-of-band callbacks.

What it was

The database can restore a snapshot from a URL. On the self-hosted build that is a documented feature; in the cloud, the docs said outbound URL recovery was turned off. The code told a different story. The fetch client had no SSRF guard, and the feature was live on the cloud data plane. So any authenticated customer, with a standard API key, could make the service send an HTTP request wherever they wanted. A plain server-side request forgery, on the one feature the docs promised was safe.

How I confirmed it

Reading source is a claim, not proof, so I made the request actually leave the building. Pointed at an out-of-band listener, the service fired back twenty-two DNS callbacks from the provider's own cloud IP ranges: blind SSRF, confirmed on the wire. Then I showed loopback reach. The backend could hit services bound to 127.0.0.1 on the host, and the HTTP status code told me what was and was not listening.

Where it stopped mattered just as much. External HTTP egress was filtered, the cloud metadata endpoint gave up no credentials, and private-range and file:// destinations were blocked. Real and reachable, then, but bounded: Low to Medium, not an internal-network compromise. I reported it at that severity rather than talking it up.

How it resolved

The security team closed it as already reported, a duplicate. No bounty, but it confirms the finding: another researcher had found the same SSRF and the vendor agreed it was real. It was just already on their desk.

I have left the company unnamed because the report was handled privately and never disclosed.
