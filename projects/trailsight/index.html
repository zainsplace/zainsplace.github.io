Trailsight

A self-hostable tool that reads AWS CloudTrail logs and flags identity and API attacks on small accounts. Rules decide what is a threat. An optional local model explains the finding, and nothing else.

The problem

GuardDuty tells you a severity, not the reasoning, and it can't be self-hosted or extended. Wiz and Datadog are priced for companies. Panther and Falco are strong but heavy to run. A solo developer or a three-person startup on AWS usually ends up running nothing, or running GuardDuty and ignoring alerts they can't interpret.

Trailsight is aimed at that user. It covers one data source, CloudTrail, and one threat class, identity and API abuse. It is free, runs on your own machine, and every finding carries the events that caused it.

How it works

CloudTrail JSON export
        |
        v
Loader       one Event per record
        |
        v
Six rules    each runs over every event
        |
        v
Findings     severity, identity, evidence
        |
        +-- optional --> Ollama (local)
        |                explains a finding
        v
CLI: text, JSON, exit code
Dashboard: local Flask app

The loader takes a CloudTrail export, either {"Records": [...]} or a bare list, and normalises each record into one event: time, API call, service, region, identity ARN and type, access key, source IP, error code, whether MFA was used, and the request parameters. Nothing after the loader knows where the logs came from.

Each rule is a plain function over the full list of events that returns findings. A finding holds the rule, a severity, the identity, a one-line summary, and the exact events that triggered it. The CLI prints findings as text or JSON and exits with status 1 if there are any, so a scan can fail a CI job. The dashboard shows the same findings as cards, sorted by severity, with the evidence one click away.

The six rules

RuleFires whenSeverity
Leaked credentialsOne access key is used from two or more different source IPs inside any one-hour window. Reports only the burst, once per key.High
Privilege escalationAttachUserPolicy, AttachRolePolicy or AttachGroupPolicy with a policy ARN containing AdministratorAccess.Critical
ReconnaissanceOne identity makes 15 or more calls starting Describe, List or Get within 30 minutes. Once per identity.Medium
Security controls disabledStopLogging, DeleteTrail, DeleteDetector or DisassociateFromMasterAccount.Critical
Root activityAny event by the root identity, except ConsoleLogin.High
Console login without MFAA ConsoleLogin where CloudTrail does not record MFA as used.Medium

Rules detect, the model explains

The language model sits at the end of the pipeline. It is only ever handed a finding the rules have already made, with that finding's evidence, and asked what happened, why it is suspicious and how to respond. It is never asked whether something is malicious, and the prompt tells it to use only the evidence given.

That split is deliberate. Detection is code, so it can be tested and gives the same answer every time. A model can be wrong or make things up, so it never gets a vote on what counts as a threat. Turn explanations off and the findings are identical. They are off by default and run through Ollama on localhost, so logs never leave the machine.

Testing, and what I measured

The repo has 93 tests: 18 for the rules, each with a case where it fires and a case where it stays silent, plus the loader, the CLI, the dashboard, the launcher and the explanation layer. The explanation tests swap the model for a fake and check what it is sent, so they run without Ollama. GitHub Actions runs ruff and the full suite on Python 3.12 on every push and pull request, and CodeQL scans the code.

I ran the generator and the scanner myself on 13 October 2026:

Read that result for what it is. The dataset is small and each attack was written to trip its rule, so it shows the rules are wired up correctly, not how well they do on real logs. The end-to-end test also only checks that every planted rule fires, so a false positive would not fail it.

What it misses

I fed the rules hand-built events to find the edges. Each of these went through without a finding:

  • Admin rights granted any other way: an inline policy with PutUserPolicy, a new policy version with CreatePolicyVersion, or adding a user to an admin group.
  • A root console login. Root activity skips ConsoleLogin, and the MFA rule only fires when MFA is missing.
  • Enumeration that stays under 15 calls in 30 minutes, or is split across two identities.
  • Quieter ways to blind logging: UpdateDetector to disable GuardDuty, PutEventSelectors to narrow a trail, deleting the log bucket, or stopping the AWS Config recorder.

And these fired when they arguably shouldn't:

  • A denied AttachUserPolicy still raises a critical finding, because no rule looks at the error code.
  • A federated sign-in, where MFA happens at the identity provider and CloudTrail records it as not used, is reported as a login without MFA. So is a failed login.
  • A role whose key appears from two AWS service addresses within an hour is flagged as leaked.
  • An application role making 20 GetObject calls in ten minutes counts as a reconnaissance burst, because Get covers normal data reads too.

Beyond the rules, it reads one uncompressed JSON file at a time. It can't pull from S3 or CloudWatch yet, and the per-identity baseline and the correlator in the design doc aren't built.
